Supply chain

Supply chain

Every package in ghcr.io/go-pkgx/packages ships with the evidence needed to audit and trust it. Three artifacts are attached to each package as OCI referrers, so they travel with the image and are discoverable from its digest:

  • a CycloneDX SBOM — the package’s components and versions (go-attest/sbom);
  • an in-toto SLSA provenance statement — how and from what the package was built;
  • a cosign-style + minisign signature over the package (go-attest/sign).

What went IN, not only what came out

Those three describe the output. Until recently nothing recorded the input: of 1858 recipes with a source URL (measured 2026-09; re-counted 2026-10-05 as 1874 distributable URLs across 1899 recipes, reaching 233 distinct upstream hosts), exactly one declared a checksum, and none was verified. A source tarball that changed upstream produced a different package, correctly signed, attesting a URL rather than the bytes that came back from it.

The provenance now carries the source as a SLSA resolvedDependency — the archive’s SHA-256, or a git checkout’s commit:

"resolvedDependencies": [{
  "uri": "https://github.com/ROCm/ROCR-Runtime/archive/refs/tags/rocm-7.2.4.tar.gz",
  "digest": {"sha256": "60532cd86edce5a603aa18df406ec1f5a3d18f0663d79b3b7822ff721c5a04ec"}
}]

It records the candidate URL that answered, which for a recipe listing mirrors is not always the first one — a build that fell through to a mirror and one that did not are different builds.

And where a recipe declares a sha: URL — the form the pkgx format already had and nothing read — the digest is verified. A mismatch fails the build rather than falling through to the next mirror: a build that quietly succeeded from a second host after the first served unexpected bytes would hide the one event that check exists to surface.

And where a recipe declares nothing, which is 903 of 904

Verifying a declared sha: is worth having and reaches almost nothing. Measured on 2026-10-05 against a fresh pkgxdev/pantry: one recipe of 904 carries a sha: at all, and that one — openssl.org — points at ${{url}}.sha256, a file served by the same host as the tarball. It catches corruption in transit, which TLS already catches. It does not catch substitution: a host serving different bytes serves a matching .sha256 beside them.

So the source mirror grew a second job. It already kept every archive a build downloads, addressed by its SHA-256; it now also records which digest each URL served, and a later fetch that disagrees is refused:

fetch: this URL has served different bytes before:
  https://…/x-1.2.tar.gz now serves 2c26b4…, and served 9f86d0… before

Trust on first use. It does not make an upstream trustworthy — it makes a change visible, which is the part nobody had.

A version bump is a first use, because the version is in the URL: a new release asks a question never asked before and is recorded rather than refused. That is why there is no --no-pin escape; the case it would serve does not arise.

The uncomfortable case is a mirror that cannot be asked. That is not an absent pin, and treating the two alike is how trust-on-first-use quietly becomes trust-every-time. They are distinguished, said out loud, and --source-pin-strict chooses which is fatal — warn and continue by default, because an unreachable registry is not evidence of tampering.

It is opt-in: --source-mirror is empty unless a run asks for it. Turning it on is safe rather than risky — the mirror’s existing contents carry only content tags, so the first pass records and only the second enforces.

Still missing, and it is a decision rather than a patch: openssl.org also declares sig: ${{url}}.asc, and nothing reads that field. It is the only control in the recipe format a compromised host could not forge — the signing key is not on www.openssl.org — and honouring it needs a key policy: whose key, pinned where, and what happens when a release is signed by a new one. A verifier that accepts any key proves only that somebody signed something.

The pinned key

Signatures verify against a single pinned public key:

RWQ+rmH+fXy2iYr+gReQAOQtYWtH0A7UlxcAa2hpr+txNBwGqtpFsR6L

The factory signs with the matching private key (held only as a CI secret); every consumer checks against this exact public key.

Verify on install

The go-pkgx/bottle backend that both pkgx and pkgm import performs verification at install time:

  • bottle.VerifySignature validates a package’s signature against the pinned key.
  • Setting PKGX_VERIFY=1 makes verification fail-closed: a package with no signature, or one that does not verify, is refused rather than installed.
# refuses to install anything that isn't validly signed by the pinned key
PKGX_DIST=oci://ghcr.io/go-pkgx/packages PKGX_VERIFY=1 pkgm install lz4.org

This closes the loop end to end: the factory signs and attests at publish time, and the consumer refuses to run anything it cannot verify.

Known vulnerabilities, asked at the version we publish

Signing says these are the bytes we built. It says nothing about whether those bytes are known to be vulnerable. That is a second question, and it is asked daily, for every platform we publish, by a scheduled job in go-pkgx/packages.

The whole design is in which question it asks. Ask OSV about each package as a whole and it returns every advisory that package has ever carried — 748 findings across 21 projects over this pantry on 2026-10-17, nearly all of them fixed long before anything we ship. Ask at the version the published catalogue says we carry, and skip outright the identities a platform carries no version of (2026-10-20):

Each row adds to 1673, the identity count of the pantry — that sum is the control that no bucket is a silent drop. Unanswerable means an identity OSV is not keyed on: a repository or a CPE rather than a package in an ecosystem.

⛔ It asked about two of six until 2026-10-20

The platform list was written into the workflow, and it named linux/x86-64 and darwin/aarch64 while the registry published six — linux/aarch64 among them, the largest here by bottle count. All four of the missing ones were clean, so the cost was coverage, not exposure; but an enumeration copied into a file freezes while the population grows.

The list is now derived. The index has always known which platforms exist — a platform that is not published is refused with platform not in index — and pkgs catalog platforms asks it:

pkgs catalog platforms          # one per line, ready for --platform
go run ./vulnsweep -pantry pantry -advisories advisories -store "$PKGX_DIR"

A seventh platform is covered the day it is published, by nobody’s decision. vulnsweep prints a line per platform, keeps going after a red one — a sweep that stops at the first reports one problem and hides the rest — and refuses to sweep nothing: an empty list, a list of noise, or a list it could not obtain is an error, never the clean zero this lane would otherwise print on the day the registry stops answering.

⭐ The first derived run found three real advisories, against vitejs.dev, on four platforms — two of which had never been scanned at all. We published vite 8.2.1 and the affected range is >= 8.2.0, < 8.2.4. The remedy was a rebuild at a version npm actually publishes above the fix boundary, which is worth checking: the 8.3 line is affected too, below 8.3.3.

-fail-on-new is a verdict, not a report: a finding already recorded has a decision behind it, and one that is not is a question with an answer. The job holds contents: read and never writes to the advisory tree — recording a decision stays a pull request, by a person.

What a decision looks like, and how far it reaches

A decision is a dated event in advisories/<project>/advisories.yaml, and bk publish --advisories attaches it to the bottle as an OpenVEX v0.2.0 document, signed with everything else.

- id: MAL-2026-3020
  events:
    - timestamp: 2026-10-11T10:29:00Z
      type: detection
      detected-version: 1.22.1
    - timestamp: 2026-10-11T10:31:00Z
      type: false-positive-determination
      detected-version: 1.22.1
      justification: component_not_present

⛔ detected-version is not paperwork. A purl names a version, so a VEX statement is a claim about a version — and the emitter will not restate the two statuses that tell a reader to stop looking, not_affected and fixed, about a version no event in the record names:

record determines not_affected for 1.22.1, bottle is 1.22.1   → not_affected + justification
record determines not_affected for 1.22.1, bottle is 2026.9.1 → under_investigation + status_notes
record names no version at all                                → under_investigation + status_notes

Neither the justification nor the prose travels onto a downgraded statement: both were written about another artefact. affected is deliberately not downgraded — restating a warning for an unexamined version over-warns, which costs noise, while downgrading it would turn a warning into “we are looking into it”.

The gate and the document therefore read an absent version in opposite directions, on purpose: vulnfetch -fail-on-new treats a record that names no version as covering everything and stays green, because it interrupts us; the emitter treats it as covering nothing, because it reassures a stranger, and a stale “not affected” stops them looking. When in doubt do not interrupt ourselves; when in doubt do not reassure somebody else.

⛔ All of the above is keyed on a DECLARED dependency

Every number on this page is reached through the dependency graph. A bottle declares openssl.org ^3, the sweep asks OSV about the openssl version the catalogue says we carry, and a fix lands by rebuilding the openssl bottle. The whole mechanism rests on one assumption nothing was checking: that a declared dependency is the copy the artefact actually uses.

rpm.org/rpm-sequoia declares openssl.org ^3 on linux and links no libssl at all. A rebuild linked openssl 3.6.4 statically into the library — 4.2 MB to 12.6 MB, openssl’s own version banner inside the .so, nothing in DT_NEEDED.

A broken reference is visible: an unresolvable soname is something a sweep counts and bk unresolved reports. A vendored copy is invisible. The manifest still reads openssl.org ^3, so the scan asks about the right project at the right version and gets a true answer about a copy the bottle does not load. When openssl ships a fix, updating the openssl bottle does not change the bottle that embedded it, and its own version does not move either. There is nothing to compare.

bk unlinked asks the question backwards — which projects does a bottle declare and never link?

bk unlinked --platform linux/x86-64 rpm.org/rpm-sequoia
bk unlinked --fail --platform linux/x86-64 < recipes.txt   # as a gate
rpm.org/rpm-sequoia   declares openssl.org, which ships afalg.so, capi.so,
legacy.so, libcrypto.so, libcrypto.so.3, libssl.so, libssl.so.3,
loader_attic.so, padlock.so, and links none of them

--platform matters more here than anywhere else on this page: the one confirmed case is published for linux and not for darwin, so a host-only command could not look at the very bottle the check was written for.

A finding is a candidate, and the output says so. Two different defects leave the same trace — a vendored copy, and an edge that is simply no longer needed — and only the second is harmless. The check reports direct edges only: a transitive dependency is one nobody promised to link, so a package that declares curl.se and links no openssl has done nothing wrong. A dependency that ships no shared library at all is never reported, because it cannot be linked and declaring it says something else — a program run at runtime, a data set like curl.se/ca-certs, an interpreter.

⛔ What a finding is not, and the noise floor it has

That last rule is a heuristic, and it has a floor worth stating before you read a list rather than after.

A program dependency whose bottle also ships a library is reported, and should not be. gnome.org/glib declares python.org, and its recipe says why — “several of the bins are scripts”. Nothing links libpython, but python’s bottle ships one, so the silence rule does not fire. The same happens for gnu.org/coreutils, whose bottle contains exactly one .so (libstdbuf.so, an LD_PRELOAD helper nobody links). Read those as declared for a program, not as defects.

A platform-split dependency is a real finding, not noise. gnome.org/glib also declares gnu.org/gettext: ^0.21 for every platform, and on Linux that is dead weight: libc.so.6 of glibc 2.44 exports gettext, dcgettext, dgettext, bindtextdomain, textdomain and ngettext itself, so nothing links -lintl there. GNU libintl is needed where libc lacks those — macOS. Ten projects in this pantry declare gettext unsplit; every Linux consumer installs it for functions already in libc.

The check sees DT_NEEDED, never dlopen. A plugin host that opens its providers at runtime links none of them by design, and will be reported. That is the one case where a finding can be both correct and uninteresting.

A short history is worth keeping beside the output, because it bears on how much a clean run is worth. The first sweep of a pantry with this command produced findings that measured the command: a soname was attributed to one owner when two projects shipped a file of that name (fixed in bk v0.44.1), and a real libfolly.so.0.58.0-dev was refused for its non-numeric version suffix while a libstdc++.so.6.0.33-gdb.py had earlier been counted as a library (v0.44.2: the name is a prefilter, the magic number decides). Both were caught by a finding that was not merely surprising but impossible — C++ libraries linking no C++ runtime. Use at least v0.44.2, and treat an impossible finding as a statement about the instrument.

⛔ End-of-life is not a CVE, and OSV cannot say so

Everything above asks what is known to be wrong with this version. A release line upstream has abandoned has nothing known about it yet — and never will, because nobody is looking and no fix is coming. So the daily sweep returns a clean zero for a package whose upstream stopped issuing fixes years ago. bk eol asks the other question:

bk eol -product openssl 3.2.6 3.3.7 3.4.7 3.5.8 3.6.4 4.0.2
3.2.6        end-of-life  line 3.2 ended 2025-11-23
3.3.7        end-of-life  line 3.3 ended 2026-04-09
3.4.7        end-of-life  line 3.4 ended 2026-10-22
3.5.8        supported    line 3.5 supported until 2030-04-08 (LTS)
3.6.4        expiring     line 3.6 ends 2026-11-01
4.0.2        supported    line 4.0 supported until 2027-05-14

longest-supported openssl line: 3.5 (LTS), until 2030-04-08

Judged on 2026-10-29, when ^3 took the newest 3.x — 3.6, three days from the end of its line — while 3.5 LTS ran to 2030 and was already in the registry. Nothing in the CVE lane could say that.

A finding names its destination, because “3.6 ends on Sunday” is a problem and “3.5 is supported to 2030” is the next step. -fail makes it a gate and -within sets what counts as expiring.

And then Sunday came

Those six versions are not all this registry publishes. Measured on 2026-11-01, openssl.org carries 72 tags across nine lines — 1.1.1, 3.0 and 3.1 as well — of which seven are end-of-life and two supported:

lineverdict
1.1.1ended 2023-09-11 (LTS)
3.0ended 2026-09-07 (LTS)
3.1ended 2025-03-14
3.2ended 2025-11-23
3.3ended 2026-04-09
3.4ended 2026-10-22
3.6ended 2026-11-01
3.5supported to 2030-04-08 (LTS)
4.0supported to 2027-05-14

A gate that reports a problem on the day it arrives has still left everyone on the abandoned line, so since pkgx v0.30.0 the resolver acts on the verdict:

$ pkgx --graph --platform linux/x86-64 +openssl.org@^3
openssl.org 3.5.8

It is a rank, not a filter. =3.6.4, ^3.6.4, ~3.6 and every lock still resolve to 3.6.4 — nothing supported satisfies them — and say so on stderr:

pkgx: openssl.org 3.6.4 is on end-of-life release line 3.6 and nothing
      supported satisfies "=3.6.4"; using it

Reproducibility outranks the preference: a lock that stopped resolving would be a worse defect than the one this fixes. So the preference changes an answer only where a supported candidate also satisfies the constraint, which is why it can never reach across a soname boundary — ^3 and ^4 share no satisfier.

The one answer that moves stays inside libssl.so.3, and its ABI cost was measured rather than assumed: 3.6.4 exports 6499 symbols and 3.5.8 6476, so 23 symbols are the whole of the risk (the new KEM CMS_RecipientInfo_kemri_*, the CRYPTO_*_array allocators, EVP_SKEY and friends). Across the ten heaviest consumers — curl.se, openssh.com, python.org, ruby-lang.org, postgresql.org, nodejs.org, php.net, erlang.org, openldap.org, libssh2.org — 45,601 imported symbols, none of them on that list. A sample of ten out of ~160 runtime dependents, not a proof about all of them.

PKGX_DEPRECATED names a JSON file that replaces the built-in list, {"openssl.org": ["3.6"]}; {} turns the preference off. A named file that cannot be read or parsed is an empty list and a warning, never a silent fall back to the built-in one: naming a file is a statement about what you want, and substituting something else would hide the mistake behind behaviour that looks like it worked.

The build side is not there yet. bk resolves build-time dependencies through the same resolver and does not carry the list, so the factory still builds against 3.6.4 what pkgx now runs against 3.5.8 (go-pkgx/bk#378). The list also still lives in the binary rather than in the signed catalogue, where it would be computed instead of committed (go-pkgx/bottle#179).

The field that would have inverted the verdict

endoflife.date reports, for openssl:

{"name":"1.1.1","isEol":true,"eolFrom":"2023-09-11","isMaintained":true}
{"name":"3.0",  "isEol":true,"eolFrom":"2026-09-07","isMaintained":true}

Both lines have been out of support for a while, and both say isMaintained: true — it reflects the paid extended support openssl sells. A check reading that field would report 1.1.1 as healthy, and this pantry has 32 bottles linking it. bk eol reads isEol and the date, never isMaintained; the field is not decoded into the type at all, so no later reader can reach for it by accident. An absent date is reported as unknown, never as supported: nobody committing to a date is not the same as a date far away.

Metadata is not a program, and a key is not a caption

Signatures cover the bytes. The strings beside them — a project’s name, its summary, the commands it provides, its versions and platforms — reach your terminal before any of that is checked, and they are written by people who are not you: an upstream recipe author, whoever wrote the lock you were handed, whatever registry PKGX_DIST points at.

Measured, with a crafted lock:

$ pkgx --lock esc.lock.hcl true | cat -v
pkgx: no version of zlib.net satisfies "=1.3.2\x1b[2K\r…" (available: 2);
  asked for by =1.3.2^[[2K^Mzlib.net  1.9.9  ✓ verified (requested)

ESC[2K erases the line and \r returns the cursor, so on a terminal that line rubs itself out and reprints as something reassuring. The same hole was in the catalogue, where pkgs ls printed versions straight through.

Three treatments, and which one applies depends on what the field is and who writes it:

fieldtreatmentwhy
project namethe whole file is refuseda name becomes a URL and a path; a bad one means somebody wanted something
summary, providescleaned and showncosmetic — refusing a catalogue over one paragraph would deny service for a typo
version, platform in a lockthe whole file is refusedexactness is the entire point of a lock
version, platform in a cataloguethat entry is dropped, the file is kept, and the count is printedthese come from an upstream recipe’s versions:, so refusing would hand any recipe author a switch that turns off pkgs ls, search and every <TAB> for everyone
a tag from the registryskippeda registry is a configured endpoint

A key can never be cleaned the way a caption is: a cleaned key would select something other than what it says. So it is refused or dropped, never silently repaired.

$ pkgs catalog
~/.pkgx/catalog/darwin-aarch64.json
1908 project(s), 956 with dependencies, 2 hour(s) old

If a catalogue ever carried an unreadable version, a third line would say so — 1 version string(s) were unreadable and are not listed. On a catalogue our own factory published it should never appear.

The allowlist was measured before it was written: across the two catalogues published on 2026-10-06, 2801 version strings use fifteen distinct runes and the longest is 19 bytes. What is accepted is deliberately wider than that, because a guard that refuses the ordinary case is a worse bug than the one it fixes.
