Build isolation

Build isolation

Packages are only as trustworthy as the environment that produced them. The factory builds in two phases, one shipped and one experimental.

Phase A — debian container (shipped)

Builds run inside a pinned debian:stable-slim container rather than on the drifting GitHub-runner host. This gives:

  • a controlled, known glibc floor instead of whatever the runner ships;
  • no host-tool leakage into the build — only the declared base plus pkgx-sourced dependencies are present;
  • reproducible output across runs.

This is the isolation model in use for every published package today.

Phase B — FROM-scratch pkgx-glibc toolchain

Phase A still links against the container’s glibc. Phase B goes further: build against pkgx’s own glibc toolchain so packages are truly self-contained and run on a literally-empty FROM scratch base with no system libc at all.

It is shipped, and it is the default. The factory’s sovereign input says so in its own description: blank builds inside the FROM scratch rootfs bk builder stages, “so neither the host’s libc nor its compiler takes part”, and 0 is what falls back to the runner’s distribution.

  • bk build --libc=pkgx and bk factory --libc=pkgx target the gnu.org/glibc bottle — its crt objects, its libc, its dynamic linker — instead of the container’s;
  • --glibc <version> pins that sysroot to an exact glibc line;
  • bk builder stages the rootfs itself: static Go binaries plus toolchain bottles from the signed registry, nothing else;
  • design note: bk/docs/from-scratch-toolchain.md.

Corrected 2026-10-27. This page previously described Phase B as experimental, living on branch feat/pkgx-glibc-toolchain, and gated behind a BK_PKGX_LIBC=1 environment variable. All three were out of date: the work is on main, the gate is the --libc flag above, and BK_PKGX_LIBC appears nowhere in bk’s code — only inside the design note that first proposed it.

What a sovereign toolchain does not reach

The sysroot, the -isystem directories and the runtime choice reach a build through the compiler driver — cc, which is bk’s own shim and re-execs $BK_CC, or $CC. A tool that drives the compiler some other way sees none of it.

bindgen is that tool: it calls libclang in-process. A Rust crate generating bindings therefore got the container’s idea of a libc, or none at all —

/pkgx/openssl.org/v3.6.4/include/openssl/asn1.h:27:10:
  fatal error: 'stdio.h' file not found

— in a build where openssl 3.6.4 had been found, probed and configured correctly a few lines earlier. Since bk v0.43.0 sovereign mode also exports BINDGEN_EXTRA_CLANG_ARGS, the variable bindgen’s own documentation names for exactly this, carrying the header-finding flags only and appended to whatever the recipe set.

See Running pkgx packages on FROM scratch for why a system-linked package needs closure completion to run on scratch, and what Phase B removes.
